

## Large upload batches and scheduled distribution

Web and mobile now upload via `/calling-lists/batches`, then `PUT /calling-lists/batches/:batchId/file`. Limits: one worksheet, up to 100 MB compressed, 768 MB declared ZIP expansion, 50 columns, 2,000 characters per cell and 1,000,000 nonempty candidate rows. Headers must be unique and nonempty. Workbook rows are streamed and saved as text into separate private S3 workbooks containing 50 candidates plus headers (the final sheet can have fewer). Each name includes the batch ObjectId and part number; retries reuse the same names and list IDs.

Only metadata is stored in MongoDB before assignment: batch progress and sheet title, S3 location, headers, counts, upload identity and assignment state. Candidate cell values remain in S3. `candidateStorage: S3` previews read the file directly and cannot modify status, delete candidates or convert CPs. Counts show zero calls/deletions and all entries as not called. MD and all MIS users can view/manage bulk sheets. RMs cannot see unassigned sheets; CP Heads retain read-only access to sheets assigned to their downline. Existing legacy MIS ownership rules remain for older uploads.

The server starts a recoverable background worker after connecting to MongoDB. It checks every 30 seconds. QUEUED batches are processed one at a time per server; PROCESSING batches have a renewed 20-minute ownership lease. Partial sheets stay STAGED and hidden until the batch is published transactionally. Failed imports show a retry option. Large processing can take time because every generated workbook is a separate S3 object. Progress is refreshed manually in both clients. ExcelJS uses the operating system temporary directory while streaming some workbooks; provision writable temporary disk space (configure TMPDIR if necessary) and adequate process memory for its shared-string cache.

Automatic distribution starts at 09:30 Asia/Kolkata each day (up to 30 seconds after that time while the server is running). A same-day restart catches up remaining allocations; previous days are not replayed. It assigns one unassigned, never-imported bulk sheet per active RM per day, even if earlier work remains. MD/MIS can disable automation or wait until earlier sheets have no NOT_CALLED candidates. The daily quantity is fixed at one sheet per RM; each sheet still contains up to 50 candidates. RMs are rotated daily and allocated one round at a time when the pool is short. If sheets become ready later that day, subsequent checks fill missing daily slots. Manual assignments are separate from the automatic daily quota.

Assignment verifies the S3 workbook against stored metadata, then atomically imports candidates, sets RM/storage state and (for automatic assignments) records a unique IST-day/RM/slot allocation. Unique indexes and conditional updates prevent duplicate imports or allocations across retries and multiple backend instances. Normal calling statuses, CP conversion, hard deletion and reports apply after assignment. Removing an assignment later preserves candidate work and history; such sheets are not returned to the automatic pool. Existing pre-feature rows are not deleted or migrated.

The scheduler requires the backend service to be running at the scheduled time, MongoDB replica-set transactions, private calling-list S3 access and the new collection indexes. Startup creates the required indexes in production. No external cron installation or new package is required. A reverse proxy in front of the API must allow 100 MB uploads if this full limit is needed.

Checks: backend unit and HTTP tests; `node tests/calling-bulk-scale.test.mjs` covers 100,001 rows and 2,001 chunks; `CALLING_BULK_DB_TEST=1 node tests/calling-bulk.db.test.mjs` uses a uniquely named temporary database and mocked S3 for preview privacy, concurrent allocation, manual import, rollback, inactive-RM exclusion, settings and failed-batch recovery. It removes only its temporary database.
